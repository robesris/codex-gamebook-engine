Development changelog for the Codex Gamebook Engine: the codex doc (`gamebook_codex_v2.md`), the GBF schema (`codex.schema.json`), and the reference emulators (`cli-emulator/play.js`, `index.html`). Versions move together.

## v2.16.0

`modify_stat.set_initial_to` — first-class encoding for absolute stat caps (Rule 30 cap-pattern). Schema bumped to GBF 1.12.0; both reference emulators bumped to 3.7.0. Closes one of the v2.15.x / v2.16.x backlog items the Chat #24 series tracked: pre-v1.12 the canonical encoding for an absolute ceiling cap ("from now on your STRENGTH cannot exceed 11" — Windhammer §440; "your maximum ENDURANCE is now N" — Windhammer §533) was a `script` event clamping both `state.initialStats[stat]` and `state.stats[stat]` via the section-level Lua sandbox per Rule 30's documented workaround. v1.12 adds `modify_stat.set_initial_to: <value>` so the same mechanic encodes as a single `modify_stat` event. **Semantics.** When present, the emulator assigns `state.initialStats[stat]` to the supplied absolute value and clamps `state.stats[stat]` down if currently above the new ceiling; a current value already at or below the cap is left unchanged (raising a ceiling does not auto-heal). Excluded for the resource slots (`provisions` / `gold` / `meals`) since they are tracked on state directly rather than via `state.initialStats`. **Composability.** Composable with `amount` and `modify_initial` on the same event — the emulator applies `amount` first (with `initial_is_max` clamping using the OLD ceiling), then `set_initial_to` reassigns the ceiling and clamps the (already-modified) current value if needed. The canonical encoding for a pure cap omits `amount` and `modify_initial`; if a section combines a heal with a cap, encode the heal in a separate prior event for auditability. **Rule 30 updates.** The cap-style subsection rewrites the script-event workaround as the historical pre-v1.12 encoding and presents `set_initial_to` as canonical with worked example using Windhammer §440. The verification subsection adds a third check covering `set_initial_to`-encoded caps (cap value matches stated ceiling, no spurious `amount` or `modify_initial`). **Decision-table row updated** keyed on stat-cap source-text language ("cannot exceed N," "your maximum is now N") to point at the `set_initial_to` encoding rather than the script-event workaround. **Pre-output checklist** Rule 30 entry expanded with the cap-pattern check. **Test coverage:** `tests/run.js` Test 21 covers the three behaviors a regression must preserve — (a) initialStats is assigned the absolute value, (b) current is clamped down when above the new ceiling, (c) current is left alone when already at or below the new ceiling. Test 20's schema-title assertion bumped to v1.12.0. 21/21 tests pass. **Ship vehicle:** codex doc, schema, both reference emulators, tests, package.json all move together. All four maintained books (LW1, Warlock, GrailQuest, WWY) remain valid against schema v1.12.0 — the change is strictly additive (a new optional field on `modify_stat` events). The Windhammer accumulator's pre-existing script-event cap encodings at §440 / §533 are now migration candidates for sub-agent rewrite to the `set_initial_to` encoding; Rule 30's anti-pattern callout for the script-event workaround makes those sites surface in a future migration pass. **HTML emulator's undocumented `modify_initial_amount` divergence** (Chat #24 process lesson #6, Pending Item #15) is unchanged — this release does not touch that field.

## v2.15.4

Pattern 7.6.11 (Compound stat-test reducible by skill / talent / item). Codex-doc-only release; GBF schema v1.11.0 / CLI emulator v3.6.0 / HTML emulator v3.6.0 unchanged. Closes the §594 compound-stat-test reducible-by-skill pattern decision Chat #23 left open as one of the v2.15.x backlog items (third compound-stat-test instance in Windhammer, joining §352 luck+agility and §485 strength+intuition). The motivating distinction: §352 / §485 are pure Pattern 7.6.2 (compound stat gate, no reducibility); §594 is genuinely different — STRENGTH + AGILITY compound test reducible to AGILITY-only when the player has `talent_strong_back` (Rule 27 flag). Pattern 7.6.2 alone is insufficient because the reducibility lives in player state, not in the roll. **Canonical encoding.** A single `script` event that reads the gating flag/item/ability ONCE before rolling, branches the comparison (single-stat if the gate passes, compound if not), rolls ONCE, sets `player.navigate_to`. The roll itself is one call to `roll()` regardless of which branch is taken — the source text always describes one roll, and the encoding preserves that. Worked example uses the Windhammer §594 STRENGTH + AGILITY case with `talent_strong_back` reduction. **Variants documented.** The reducibility gate can be a skill/talent flag (Rule 27 — most common case in skill-based books like the Windhammer family), an inventory item, or a Lone Wolf-style discipline (Rule 15 ability). All three use the same single-script-with-internal-branching shape; only the global table the script reads from differs (`flags` vs. `inventory` vs. abilities table). **Anti-pattern callout.** Splitting the reducible test into two `stat_test` events gated by `has_flag` and `not has_flag` implies TWO rolls — the source text describes ONE. The two-event encoding lets the player consume Luck on the failure of either, which mis-encodes the source-text intent. Always one `script` event for the reducible case, branching internally on player state. **When NOT to use Pattern 7.6.11.** If the source text describes the reduction as a *separate* sequential check ("first test STRENGTH; if you fail, then test AGILITY with Strong Back as a second chance"), the encoding is two sequential `stat_test` events with appropriate `target` chaining, not one compound script. Pattern 7.6.11 is specifically for *one roll, one of two comparisons*. **Decision-table row added** keyed on "Compound stat test reducible by a skill / talent / item — 'Roll 2d6, total ≤ both your STRENGTH and AGILITY (or AGILITY only if you have Strong Back)'" pointing at Pattern 7.6.11. **Pre-output checklist** unchanged (Section 7.6 patterns are documented as recognition guides, not as Rules with their own per-rule checklist entries — though the Rule 13 / 14 / 22 cross-reference checks already cover stat_test / script-event verification implicitly). **Ship vehicle:** codex doc only — no schema change, no emulator change (existing `script` event mechanism handles it, the Lua sandbox already exposes `flags` / `inventory` / abilities globals as needed), no test change. Sub-agent migration of Windhammer §352 / §485 / §594 (and any other compound-stat-test sites in this or future books) is unblocked.

## v2.15.3

Rule 30 (Permanent stat modification — `modify_initial` for delta changes, script-event workaround for caps). Codex-doc-only release; GBF schema v1.11.0 / CLI emulator v3.6.0 / HTML emulator v3.6.0 unchanged. Closes the §453 / §440 / §533 permanent-stat-modification pattern decision Chat #23 left open as one of the v2.15.x backlog items. The motivating discovery: `modify_stat.modify_initial: true` already exists in the schema (`codex.schema.json:690`) and is implemented by both reference emulators (CLI: `cli-emulator/play.js:1057-1058`; HTML: `index.html:2261-2264`) — when set, the `amount` delta is applied to BOTH `state.stats[stat]` AND `state.initialStats[stat]` so `initial_is_max` clamping prevents healing from restoring beyond the new ceiling. The §453 case (`STRENGTH permanently reduced by 3`) maps directly to `{type: "modify_stat", stat: "Strength", amount: -3, modify_initial: true}`. Rule 30 documents the canonical encoding so sub-agents migrating Windhammer don't invent a workaround. **Discriminating words.** *Permanently* / *forever* / *initial* / *for the rest of your adventure* / *cannot recover* → `modify_initial: true`; absent → omit the flag (transient loss). **Three-layer duration framing.** Per-fight (combat modifier per Rule 17) vs. per-section (transient `modify_stat` without `modify_initial`) vs. permanent (`modify_stat` with `modify_initial: true`). The discriminating tests for each layer come from the source text's temporal qualifiers. **Cap-style permanent reduction (script-event workaround).** §440 (STRENGTH cap=11) and §533 (ENDURANCE cap) describe absolute ceilings rather than deltas. The current schema has no `modify_stat.set_initial_to: <value>` field — it's tracked as a v2.16.x backlog item. Until that ships, the canonical encoding is a `script` event that clamps both `state.initialStats[stat]` and `state.stats[stat]` to the cap value via the section-level Lua sandbox. Verbose but mechanically correct; sub-agents document the cap with a short `reason` field on the script event so future maintainers can find these sites for migration when the schema field lands. **Anti-pattern callout.** A `modify_stat` with `amount: -3` and no `modify_initial: true` reduces only the current value; the player who later eats a Meal gets healed back up to the original initial — undoing the "permanent" reduction silently. The omission is an easy parser miss to introduce and a hard one to notice during play; the verification check is a hard gate. **Decision-table rows added** for both the delta and cap encodings keyed on permanence language and absolute-ceiling language. **Pre-output checklist** gains a Rule 30 entry. **Ship vehicle:** codex doc only — schema field is pre-existing, both emulators already implement it, no test change needed (existing emulator behavior is unchanged). Sub-agent migration of the Windhammer §453 / §440 / §533 sites and any other permanent-stat-reduction sites is unblocked. **Tracked v2.16.x backlog item:** schema additive `modify_stat.set_initial_to: <value>` for the cap pattern (so script-event workarounds for §440 / §533-style sites can migrate to a single `modify_stat` event); both emulators get a small handler addition.

## v2.15.2

Rule 29 (Combat-loss death — inline death without a numbered death section). Codex-doc-only release; GBF schema v1.11.0 / CLI emulator v3.6.0 / HTML emulator v3.6.0 unchanged. Closes the combat-loss-death pattern decision Chat #23 left open as one of the v2.15.x backlog items — the brief offered three options ((a) `loss_is_death: true` flag on combat event; (b) synthetic death-section generator in engine; (c) keep the narrative convention) and Rule 29 picks (c) on the grounds that the existing emulator code already implements it correctly. Both reference emulators handle the inline-death case via the standard combat-end check: when player health hits 0 inside a combat, both immediately set a death pause regardless of whether `lose_to` is set (CLI: `state.pause = { type: 'ending', ending_type: 'death', text: 'You have been slain in combat.' }` at `cli-emulator/play.js:2480`; HTML: `showEnding({ text: 'You have fallen in combat. Your adventure is over.', ending_type: 'death', ... })` at `index.html:3310`). The Windhammer pattern (40 inventoried sites with `flee_to: null + win_to set` and no `lose_to`) is therefore already correctly handled — the missing `lose_to` is not a parser miss, it is the canonical encoding for combats whose loss is death without a numbered death section. **Discriminating test.** For every combat event, ask: did the source text enumerate a section ID to navigate to on loss? If yes → `lose_to: <id>` (a numbered death section, or a survivable-loss section). If no — source says "if you lose, you die" without a section number, OR describes the loss as inline death narrative, OR says nothing about losing — `lose_to` absent and the emulator handles it. **What this rule is NOT.** Rule 29 does not introduce a `loss_is_death` flag, a synthetic death-section generator, or any new schema/emulator behavior. The point is to document the existing canonical encoding so sub-agents migrating books like Windhammer don't invent a workaround — leaving `lose_to` absent and `flee_to: null` is the right pattern, not a flag-for-review case. **Per-encounter death narrative (deferred to a future schema extension).** Both reference emulators currently use a generic death-pause text. A future schema extension may add `combat.loss_text` for per-encounter narrative customization ("the dragon's flames consume you"); until then the generic text is acceptable. Books with strongly-flavored death narratives can put the narrative in the section's `text` (where it appears before combat starts and the player has read it before fighting) rather than relying on the death pause. **Decision-table row added** keyed on "Combat encounter where the source text says 'if you lose, you die' / frames the loss inline / does NOT enumerate a numbered death section to navigate to on loss" pointing at Rule 29. **Pre-output checklist** gains a Rule 29 entry encoding the discriminating test ("did the source text give a section ID to navigate to on loss?"). **Ship vehicle:** codex doc only — no schema change, no emulator change (both already implement the canonical mechanism), no test change. Sub-agent migration of Windhammer's 40 inline-death combats is unblocked by this commit; book-side work happens in a future chat against this rule.

## v2.15.1

Rule 28 (Ending classification — `ending_type` discriminating tests). Codex-doc-only release; GBF schema v1.11.0 / CLI emulator v3.6.0 / HTML emulator v3.6.0 unchanged. Closes the §600 sequel-teaser ending decision Chat #23 left open as Process Lesson #6 — the four `ending_type` enum values (`"death"` / `"victory"` / `"neutral"` / `"continuation"`) have existed in the schema since v1.0 (and the HTML emulator's v3.0.2 fallback fix already handles all four correctly), but the codex doc had no rigorous discriminating tests for *which* type to apply when the source text was ambiguous between them — particularly between victory and continuation for sequel-teaser sections that wrap up the immediate stakes but pivot the narrative to a follow-on book. **Discriminating tests.** Death: terminal-failure language ("Your adventure ends here," "Your quest has failed," "You are dead") OR narrative defeat without literal death (locked in tower forever, transformed into stone, taken as slave) — the source text's failure framing is the discriminator, not literal mortality. Victory: closing-celebration that *concludes the narrative here* ("VICTORY!", "THE END", "the quest is complete," "peace returns to the land"). Continuation: opening-the-next-narrative that *pivots to a sequel* ("Your adventure continues in [Book N+1]," "and so begins your next quest," recap-without-"THE END" sequel-teaser epilogues). Neutral: ambiguous-non-death (cyclical, philosophical-rest, escape-without-resolution) — used sparingly, since most "the player walks away" endings are actually deaths or victories under careful reading. **Discriminator vs. victory for continuations:** ask "does the source text close the narrative, or open the next one?" Closing → victory; opening → continuation. **Where the lists live (cross-references Section 2.1a from v2.15.0):** continuation and neutral sections go in `victory_endings` (categorically non-deaths); death sections go in `death_endings`. The granular four-way classification lives on each section's `ending_type`; the top-level / confidence lists are a binary death-vs-non-death partition. **Worked examples.** LW1 §350: the player completes Book 1 and the text reads "Now turn to the next book in the series, *Fire on the Water*…" → `ending_type: "continuation"`, listed in `victory_endings`. Windhammer §600: recap of the player's defeat of the Earth-and-Stone book-2 sequel-teaser without a "THE END" banner → migrate from the pre-Rule-28 `"victory"` classification to `"continuation"`, leave the section in `victory_endings`. The HTML emulator's existing v3.0.2 fallback renders the appropriate "TO BE CONTINUED…" gold frame without further changes. **Decision-table row update:** new row keyed on "Section ends the adventure — text says [terminal-failure / closing-celebration / sequel-teaser / ambiguous]" pointing at Rule 28. **Pre-output checklist:** new Rule 28 entry covering ending_type non-nullability for `is_ending: true` sections plus the sequel-teaser re-classification audit. **Ship vehicle:** codex doc only — no schema change, no emulator change (the HTML emulator's v3.0.2 ending-color fallback already handles all four `ending_type` values correctly), no test change, no book change in this commit. **Follow-up book-side work for future chats:** an audit pass over each maintained book's `ending_type` field on every `is_ending: true` section, re-classifying any pre-Rule-28 sequel-teaser-as-`"victory"` cases to `"continuation"`. LW1 §350 already correctly carries `"continuation"` per the v2.8.3 fix. Windhammer §600's reclassification is a sub-agent task once Windhammer is promoted out of `claude_session/` per the v2.15.0 follow-up.

Both shapes are canonical and schema-valid. Schema v1.11 broadens `metadata.confidence.{death,victory}_endings` to `oneOf [array, integer]` (additive — pre-v1.11 array-shaped books continue to validate) and adds optional top-level `death_endings` / `victory_endings` arrays. The Windhammer accumulator's pre-existing top-level arrays + integer counts are now schema-valid as-is — no migration needed for that file. **Section 7.5 (Derived combat stats — combat-modifier targets):** the existing "Combat-modifier targets on derived-stat systems" paragraph is expanded to bless TWO valid targeting strategies side-by-side. Component-field targeting (`player.strength`, `player.weapon_bonus`, `enemy.armor`) for bonuses with clear single-component attribution. Generic-accumulator-slot targeting (`player.attack` / `enemy.attack` even when `rules.attack_stat: null`) for bonuses without single-component attribution — surprise attacks, narrative debuffs, generic weapon-skill bonuses on books whose round_script does not split skill from weapon. Both strategies are first-class; the choice is a function of the source text's narrative attribution and the round_script's read order. New worked example using a Windhammer-style round_script (`pcv = (player.strength or 0) + (player.agility or 0) + (player.attack or 0)`) shows the accumulator-slot pattern end-to-end with a per-section combat encoding granting +2 CV from a surprise attack via `combat_modifiers: [{target: "player.attack", delta: 2, reason: "Surprise attack"}]`. Explicit anti-pattern callout: `modify_stat` events targeting the derived stat name itself (`stat: "combat_value"`, `stat: "attack_strength"`, `stat: "hit_bonus"`) silently no-op because the derived stat does not exist on the player table — it is computed inside Lua each round from its component stats — so the event writes to a non-existent slot and combat behaves as if the bonus were not there. The fix is always one of: per-fight bonuses go in `combat_modifiers` on the combat event (Rule 17) with the right component or accumulator target; persistent stat changes go in `modify_stat` on a real component stat (`stat: "strength"` etc.). The Windhammer drift Chat #23 inventoried (13 sites in §89 / §128 / §165 / §169 / §200 / §242 / §257 / §264 / §423 / §440 / §497 using event-level `modify_stat.stat="combat_value"` instead of `combat_modifiers`, plus §169 / §423 using `combat_modifiers` with non-canonical `{stat, amount}` shape instead of `{target, delta}`) is now addressable as a sub-agent migration in a future chat. New decision-table row keyed on "section text describes a per-fight bonus or penalty to the derived combat stat" pointing at Rules 14 + 17 + Section 7.5; corresponding pre-output checklist line on the Section 7 / 7.5 entry. **Rule 27 (Skill / talent flags):** the `skill_<name>` and `talent_<name>` flag convention is canonicalised for binary skills, talents, masteries, and lores the player either has or doesn't (granted at character creation, used as gates on conditional choices and events later). The flag is set during character creation via `set_flag` (in a `choose_abilities` step's accept-handler or a dedicated `set_flag` step) and gated downstream with `has_flag` exactly as Rule 15 prescribes for any other binary capability. NO new top-level `rules.skills[]` schema field — the flag convention covers binary skills cleanly without schema sprawl. The prefix is picked from the source text's framing: training / craft / lore / mastery → `skill_`; talent / gift / trait → `talent_`. The line between Rule 27 (skill) and Rule 15 (ability) is rule-of-thumb: abilities have their own UI panel and may have uses-counters; skills are bare flags with no UI beyond the flag display. Two granting patterns documented: pick-N-from-a-list (the common case, encoded as a `choose_abilities` step where each option's `accept` action sets the flag) and class-grants-skill (the less common case, encoded as a series of `set_flag` steps each conditional on the class pick). The Windhammer-family flag inventory Chat #23 surfaced (`skill_brigandry`, `skill_lorecraft`, `skill_stealth`, `skill_bushcraft`, `skill_huntmastery`, `talent_strong_back`) is now addressable via sub-agent migration. New decision-table row keyed on "rules section names a binary skill / talent / mastery / lore" pointing at Rule 27; corresponding pre-output checklist line. **Unit test coverage:** `tests/run.js` gains Test 20 covering the schema v1.11 endings-placement broadening — schema-shape assertions (top-level arrays declared, confidence broadened to `oneOf [array, integer]`, schema title at v1.11.0) plus behavioral assertions that the emulator's book-load path accepts both shapes without raising. 20/20 tests pass. **Ship vehicle:** codex doc, schema, both reference emulators, tests, package.json / package-lock.json all move together (versions-move-together convention). All four maintained-books (LW1, Warlock, GrailQuest, WWY) remain valid against schema v1.11.0 because every change is strictly additive — none of them carry top-level `death_endings` / `victory_endings`, all of them carry array-shaped `metadata.confidence.{death,victory}_endings`, and the schema's pre-v1.11 array shape is the first member of the new oneOf union. Windhammer's `claude_session/` accumulator with top-level arrays + integer counts is now schema-valid as-is. **Follow-up work for future chats:** (a) sub-agent migration of the 13 Windhammer combat-modifier drift sites under the canonical Rule 17 + Section 7.5 encoding (book-side only — Windhammer's round_script already reads `player.attack` as the accumulator slot per the script's own comment); (b) sub-agent skill-flag tagging pass over Windhammer for the seven flag inventory above; (c) the remaining nine v2.15.x items per the Chat #25 handoff; (d) `merge_batches.js` / `reconcile_chat23.js` promotion to `scripts/merge-book-chunks.js` in the engine repo with unit tests, including the integer-count vs array-shape preservation logic the v1.11 schema now expects.

## v2.14.0

Section 9.9: multi-chat parsing for long books (codex-doc-only release; GBF schema v1.10.0 / CLI emulator v3.5.0 / HTML emulator v3.5.0 unchanged). Closes a latent gap the Windhammer track surfaced: the Section 9 processing strategy assumed a single-chat workflow, but books with 400+ sections, dense rules sections, or scanned-PDF sources will overflow any single chat's context and token budget. Users attempting a single-chat parse on such books hit mid-parse context overflow with no clean resume point; the work already done is hard to carry forward, and the next chat wastes budget re-establishing context that was already built once. Section 9.9 documents the canonical chunk breakdown: **Chunk 1** is skeleton + rules + character_creation + round_script (rule-heavy, script-heavy, not section-heavy); **Chunks 2..N** are contiguous section ranges of ~100 sections each (scaled down for dense books, up for sparse), each reading the accumulating book JSON + the PDF pages for the chunk's range and emitting the sections[id] entries; **Chunk N+1** is catalog reconciliation + the Section 10 pre-output verification checklist walked front-to-back (largely mechanical, parser-driven workflow ideal); **Chunk N+2** is playability validation — probe + smoke + any Tier 3 playthroughs against the canonical emulators. For a 600-section book this totals 8–9 chats; for 400 sections, 6–7. **What the user carries between chats:** the accumulating book JSON file, a parse_notes.txt running log of deferred questions and catalog ambiguities, the running `metadata.confidence.flagged_for_review` list, and a pointer to the codex doc. **What they don't carry:** the full PDF (loaded per-chunk for its relevant pages only), prior-chunk raw narrative (structured JSON carries the text), walkthroughs (load only for Tier 3 playthrough chunks), `known_issues.md` (separate track). **Context hygiene during a chunk:** Rule 6 (no narrative echoing) is load-bearing — the specific context-budget failure mode for long-book parses is "load a 100-section range, summarise it in prose, then emit JSON" (double-read, double-write, no quality gain). Parser-driven workflow per Rule 7 is the correct model: per-chunk parser emits the chunk's JSON, the AI reviews and fixes. **Step 2b (Tier Selection) update:** new "Long books: plan multi-chat chunking up front" paragraph instructs the AI to confirm section count + source quality with the user before parsing begins, and to propose the chunk breakdown rather than attempt a single-chat parse. **Topical decision table row:** new row keyed on "400+ sections, or dense rules section, or scanned-PDF source" pointing at Section 9.9. **Known gap:** automated chunk-merge tooling (a script that merges N partial JSONs produced by separate chats into one book file) is not yet shipped; the current workflow is the AI rewrites the full updated JSON each chunk. **Ship vehicle:** codex doc only — no schema change, no emulator change, no test change, and the Windhammer backlog entry in DEV_PROCESS remains valid (Section 9.9 complements the regression plan rather than replacing it). Chat #14 produced this rule in response to the user's question "is there any way to break down a 600-section re-parse, especially if a regular user were trying to parse Windhammer from scratch" — the answer is Section 9.9, and it applies to any long book not just Windhammer.

## v2.13.0

Rule 26: point-distribution character creation (`distribute_points`) + Windhammer Bug C (book-shape validation pass + undefined-stat display harmonisation). Schema bumped to GBF 1.10.0; both reference emulators bumped to 3.5.0. Closes both halves of the Windhammer unprofiled-series stress test the v2.8 fresh parse surfaced — Bug A (no schema primitive for point-buy stat generation) and Bug C (emulators silently tolerated undefined stats). Bugs B and D were closed by v2.8.1 / v2.9.0 prominence work; with Bug A and Bug C landing here, Windhammer is unblocked for a promotion re-parse. **Rule 26 (`distribute_points` character-creation action):** schema v1.10 adds `distribute_points` to `character_creation_step.action` enum with `total_points` (integer) + `stats` (array of `{name, min, max}`). Both emulators present this as a point-buy UI during character creation — CLI exposes a `distribute <stat>=<n> ...` action with sum-equals-total-points and per-stat range validation before committing; HTML renders one row per stat with `+` / `−` buttons, a remaining-points counter, and a Confirm button that disables until the allocation is valid. On confirm, every stat is written to both `state.stats[name]` and `state.initialStats[name]` so `initial_is_max` clamping on later `modify_stat` dispatches works the same as for rolled stats. Canonical example is Chronicles of Arborell (Windhammer): 50 points across Strength / Agility / Endurance / Luck / Intuition, each in [5, 11]. The rule composes cleanly with Section 7.5's "Games without `attack_stat`" pattern: point-buy stats serve as the component inputs for a derived attack stat computed in the round_script — neither rule is redundant. Adjacent point-buy patterns (equipment point-buy, ability-slot point-buy, weighted-cost allocation) are out of scope and would need separate action types if they surface. **Windhammer Bug C (book-shape validation pass):** both emulators gain a v3.5 validation pass that warns on three silent-broken cases — (a) `rules.attack_stat` naming a stat not in `rules.stats[]` (causes `player.attack` to resolve to 0 every round), (b) `rules.health_stat` naming a stat not in `rules.stats[]` (causes health display to fail), and (c) any declared stat still `undefined` in `state.stats` after `character_creation.steps[]` completes (the "declared but never initialised" case). The driving use case is Lone Wolf 2's Helghast ("immune to non-silver weapons") and compound-damage cases like a poisoned silver spear vs. a poison-immune silver-weak enemy, where the damage components must flow through the interaction filters independently. **Mechanism B: equipment framework (Rule 19).** A new structured equipment system on items_catalog entries: `equippable`, `slot` (free-form string, common suggested vocabulary: head/body/weapon/main_hand/off_hand/feet/hands/neck/finger_1/finger_2/back), `equip_timing` (always/out_of_combat/once, default out_of_combat), and `auto_equip` (default true). A new `properties` array on items holds tag strings like `silver` / `blessed` / `magical` that feed damage_interaction source filters and equipment-aware conditions. State gains a `character.equipment` map from slot to item_id. `stat_modifier.when` values `"equipped"` and `"combat"` are now honored by both emulators (previously silently ignored). Three new condition types: `has_equipped_item`, `has_equipped_in_slot`, `has_equipped_with_property`. Equipment slots hold exactly one item; auto-equip displaces the previous occupant, which stays in inventory but is no longer active. Removing an equipped item clears its slot automatically. Player-driven equip/unequip actions gate on `equip_timing` (out_of_combat items cannot be swapped during a combat event). The driving use case is LW's one-weapon-at-a-time rule (per the Mongoose Publishing reprint errata: *"You may only use one Weapon at a time in combat"*), which is canonical not an inference, and LW's implicit head/body slots for the Helmet and Chainmail Special Items. Rule 17 updated to cross-reference Rule 18 and remove the deferred "ability immunity" note. Both emulators gain new UI panels: a Damage Interactions panel next to the existing Combat Modifiers panel showing active immunities/resistances/weaknesses, and an Equipment panel in the player sidebar showing each declared slot and its occupant with click-to-unequip affordance. All three maintained first-party books (LW1, Warlock, GrailQuest) are re-run through the updated codex via comprehensive-review sub-agents in the same session to migrate their round_scripts to the new contract and to apply equipment tagging to their items_catalog entries per Rule 19. Regression story: none of the three books populates any damage_interactions this session, and none of the existing combats key on equipment, so combat outcomes are byte-identical to pre-v2.8 runs — the mechanism is in place but unexercised until future book data (LW2, etc.) populates it. Schema changes are strictly additive; the round_script contract change is the only breaking piece, and it's contained by the lockstep book migration.

## v2.7

Combat modifiers (Batch 2). Schema bumped to GBF 1.4.0 with two new optional fields: `combat_modifiers` on combat events (for per-section narrative modifiers) and `intrinsic_modifiers` on enemies_catalog entries (for per-enemy-type traits that travel with the enemy across every section it appears in). Both fields accept a list of generic `combat_modifier` objects with shape `{target: dot-path, delta: number, condition?, reason?, duration?}`. The target is a dot-path string identifying any numeric field on `player` or `enemy` (not an enum), so the mechanism works for any combat system: `player.attack` for attack-vs-attack systems (Lone Wolf, Fighting Fantasy), `player.hit_threshold` / `player.damage_bonus` / `enemy.armor` for threshold-based systems (GrailQuest, many AD&D gamebooks). The design is deliberately series-agnostic and does not assume `attack_stat` is non-null, so it works on the full range of combat systems the stress test validated. The emulator evaluates each modifier's optional condition once at combat start, freezes the resulting list, and applies the passing deltas to playerData / enemyData before each round_script invocation. Per-section modifiers and per-enemy intrinsics stack additively. Both reference emulators (CLI 2.4.0 → 2.5.0, HTML 2.4.0 → 2.5.0) implement the mechanism identically. The HTML emulator's combat panel now displays the active modifier list alongside the special_rules text box so the player sees what's in effect. New Rule 17 in the codex doc specifies the encoding with worked examples for narrative surprise attacks, torch-penalty conditionals, threshold-based damage modifiers, and per-enemy Mindshield-conditional intrinsic traits. Rule 14 (Combat Modifier Scope) updated to cross-reference Rule 17: both fields should be populated on any combat with a mechanical modifier — `special_rules` text is for display, `combat_modifiers` is for enforcement. The schema change is strictly additive; books with no modifier fields continue to work unchanged. First tested against a synthetic book verifying condition evaluation, stacking of event-level and intrinsic modifiers, both buff and debuff deltas, and modifier application to multiple target fields (player.attack, enemy.armor, player.damage_bonus). All existing playbooks (LW, Warlock, WWY, GrailQuest — 10 total) pass with 0 errors since none of them currently populate the new fields.
